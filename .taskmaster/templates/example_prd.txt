# Product Requirements Document (PRD)

## Overview  
This product replaces the Excel-based system register with an **Application Portfolio Management (APM) application**.  
It solves the difficulty of tracking attributes across all systems, adding new attributes and backfilling consistently, and enforcing access control.  

**Primary Audience**:  
- CIOs / IT Leadership  
- Enterprise Architects  
- System Owners / Application Managers  
- Change Managers / Release Managers  

**Value Proposition**:  
- CIOs get a **single source of truth** for reporting & decision-making.  
- Enterprise Architects can **map dependencies and plan roadmaps**.  
- System Owners have a **clear view of responsibilities and attributes**.  

---

## Core Features  

### System Registry  
- **What it does**: Central catalog of all systems, structured hierarchically with subsystems.  
- **Why important**: Provides a single source of truth.  
- **How it works**: Users can create/edit systems, group subsystems, and view in hierarchy.  

### Attribute Management  
- **What it does**: Allows new attributes to be added dynamically and backfilled across systems.  
- **Why important**: Supports evolving governance requirements.  
- **How it works**: When a new attribute is created, system prompts backfill across all systems.  

### Access Control  
- **What it does**: Role-based permissions for CIOs, architects, owners, and change managers.  
- **Why important**: Ensures correct governance and security.  
- **How it works**: CIOs = full access; Architects = edit + dependencies; Owners = their systems only; Change Managers = audit view.  

### Dependency Mapping  
- **What it does**: Tracks and visualizes relationships between systems and subsystems.  
- **Why important**: Helps architects plan roadmaps and understand impacts.  
- **How it works**: Supports both table-based view and visual diagrams.  

### Change Workflow (Logging)  
- **What it does**: Records all changes for auditing.  
- **Why important**: Provides accountability without blocking edits.  
- **How it works**: Audit log stores who changed what, when.  

### Reporting & Dashboards  
- **What it does**: Provides portfolio health views for CIOs and Architects.  
- **Why important**: Enables decision-making at leadership level.  
- **How it works**: Dashboards show system criticality heatmaps, hosting distribution, roadmap timelines, compliance gaps.  

---

## User Experience  

**Personas**  
- CIOs: need reports for decision-making.  
- Enterprise Architects: need dependency mapping & planning views.  
- System Owners: need to manage and update system records.  
- Change Managers: need logs to track modifications.  

**Key User Flows**  
1. Add a new system and assign an owner.  
2. Update attributes across all systems.  
3. View dependencies for a system.  
4. Run dashboards and reports.  
5. Search and filter systems.  

**UX Considerations**  
- Enterprise-style UI with structured forms, data tables, and dashboards.

## Technical Architecture  

**Stack**  
- **Frontend**: Blazor Server  
- **Backend**: .NET  
- **Database**: SQL Server  
- **Hosting**: Azure  

**Core Data Models**  
- **System** (core record)  
- **Subsystem/Application** (child system)  
- **Attributes** (flexible metadata model)  
- **Owner/User** (role-based access)  
- **Dependency** (system-to-system relationships)  
- **Audit Log** (change tracking)  

**Integrations**  
- None for MVP (self-contained).

## Risks and Mitigations  

- **Technical challenge**: Flexible attribute management could get messy → Mitigation: strong schema design with metadata model.  
- **MVP risk**: Dependency mapping visualizations may be complex → Mitigation: start with table, add visual later.  
- **Resource constraint**: Role-based access + logging may delay delivery → Mitigation: start with simple CRUD + logs.  
- **Adoption risk**: Users may resist moving from Excel → Mitigation: provide clean import/export and onboarding.
